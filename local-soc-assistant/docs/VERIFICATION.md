# Верификация и пределы проверяемости

`verification.verify(Draft, Case, Snapshot | None, chunks, ...)` не вызывает LLM.
Штатная повторная проверка: `python -m soc_assistant.cli verify --bundle FILE --out DIR`.
Результат — проверенная копия Draft, Check[] и адресные отказы. Исходный Draft
остаётся в bundle, свободный текст модели не переименовывается в доказанный факт.

## Проверяемые оси

1. **Факт.** Запись принадлежит случаю; поле входит в разрешённое представление;
   JSON Pointer разрешается в raw этой записи; source/record ID, если заявлены,
   совпадают. Равенство строгое: `1`, `1.0`, `true`, `"1"` различаются.
   Обогащение не является исходным фактом. Неверный факт удаляется из проверенной
   части, сохраняются Check, отказ и исходный черновик.
2. **Идентичность ATT&CK.** Код есть в закреплённом STIX, активен, принадлежит
   Enterprise. Итог хранится в `identity_check` независимо от содержательной проверки.
3. **Наблюдения.** Профиль проверяет raw-поля одной записи и полноту их цитирования.
   `observation_check` сохраняется даже при сломанной справочной ссылке.
   Для отсутствующего профиля — кандидат `analyst_required`, не supported.
4. **Справочная опора.** chunk_id входит в текущую выдачу, определение соответствует
   технике, документ/версия/хеш и точный срез текста воспроизводятся по корпусу.
   Просто существующая ссылка не доказывает содержание вывода.
5. **Хронология.** Время воспроизводится по raw; при неизвестных/конфликтующих часах
   сравнение не подтверждается. Связь должна повторять зарегистрированное правило,
   исходные времена, сущности, окно и delta. Произвольная причинная связь отклоняется.
6. **Срочность.** Политика и обогащение имеют версии и хеши; решение заново вычисляется
   по исходным признакам. Заявленная категория и её основания проверяются отдельно.
   Неверное основание → unknown. Общая политика используется во всех режимах;
   её точность не является эффектом LLM или RAG. `confirmation` хранится отдельно.

## Узкие профили v1.2-raw

Все требуют `Microsoft-Windows-Sysmon`, Event ID 1, image и commandLine одной записи.
Все четыре исходных поля должны быть явно процитированы.

| Код | Процесс | Обязательное условие команды | Предел |
|---|---|---|---|
| T1059.001 | powershell.exe | Имя PowerShell с границами | Не доказывает злонамеренность; pwsh вне профиля |
| T1059.003 | cmd.exe | Имя cmd с границами | Не доказывает цель и результат команд |
| T1053.005 | schtasks.exe | Имя schtasks и /create | Не доказывает успешную регистрацию задачи/закрепление |

Отсутствующий аргумент /create — недостаточность, противоречие image/команды —
`contradiction`. ParentImage и User — дополнительный контекст, не обязательное
«доказательство атаки». COM/API, GUI, XML, Security 4688 и другие техники требуют
новых условий и контрольных случаев. Сходство с исторической процедурой не заменяет наблюдения.

`support_state`: supported, contradicted, insufficient, not_verifiable.
`verdict`: supported только при успешных независимых проверках; rejected при неверных
наблюдениях/коде; analyst_required при отсутствии профиля, справочной опоры или снимка.
Сломанная ссылка при корректных наблюдениях не стирает факт наблюдения.

## Применимость рекомендаций v1.0

Произвольные инструкции модели не переходят в проверенный текст. Используются
локальные безопасные формулировки; код и команды не исполняются.

- `review_process`: корректные image и commandLine, ссылка на точный фрагмент runbook
  с условием проверки родительского процесса, явные реально отсутствующие поля.
- `collect_logs`: корректное наблюдение, фрагмент runbook об отсутствующих данных,
  явные реально отсутствующие поля для уточнения.
- `check_account`, `confirm_authorization`: правило применимости не реализовано,
  статус analyst_required даже при правильной ссылке.

Основанием предложения может быть явно индексированная гипотеза, но её истинность
не проверяется; без выполненных условий предложение не получает supported.
Статус рекомендации не означает подтверждение инцидента или эффективности реагирования.

## Отказы и неисправности

Адресные отказы содержат target, code, reason, needed и known. Различаются
invalid_event/invalid_field/content_mismatch, contradiction, insufficient_evidence,
source_unavailable/knowledge_not_found/invalid_source/source_integrity и отсутствие
семантического правила. Последнее фиксируется not_checked с оценкой аналитиком.
Техническая ошибка — errors, содержательный отказ — refusals. Они могут сосуществовать
с достоверной частью отчёта. При недоступной модели доступны observations, исходный Case
и воспроизводимая политика срочности; подтверждённые модельные выводы не выдумываются.

Декларации abstentions модели сохраняются с отметкой, что семантически не проверены.
Пустой ответ без основания даёт missing_conclusion, не «обоснованный отказ».
Произвольные гипотезы, русские объяснения и рекомендации A/B требуют ручной оценки.
