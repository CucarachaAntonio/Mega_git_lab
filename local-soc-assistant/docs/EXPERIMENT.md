# Воспроизводимый эксперимент (глава 3)

## Наборы и изоляция эталона

`evaluation/gold.json` v1.0 — прежние 24 синтетических сценария / 12 семейств.
Их исходные файлы, допустимые техники, приоритеты и разбиение не менялись.
`evaluation/controls.json` v2.0 — 10 дополнительных разработческих контролей:
легитимный PowerShell, encoded command, версия без commandLine, конфликт image/команды,
конфликт часов, неверная запись, неверное значение, неверный справочный фрагмент,
ошибочная техника, пара Suricata EVE. Связанные варианты process находятся в одном tune-семействе.
Новый контрольный набор не является слепой тестовой выборкой.

У контроля есть `assertions` (номер записи, поле и типизированное значение),
`opportunities` (возможность заключения или отказа по технике), обязательные поля,
приоритет и ожидаемые диагностические коды для заданного Draft. Эти сведения читает
только оркестратор/оценщик. В анализ, промпт и индекс они не передаются.
Готовые метки `rule.mitre` и скаляры с явным T-кодом, включая rule.description,
исключены из рабочего представления A/B/C/D и доступны в raw для аудита.

Число вариантов и повторов не увеличивает число независимых семейств.
Статистическая значимость, переносимость на реальный SOC и превосходство D не заявляются.
Признаки C намеренно соответствуют узкому инженерному корпусу; это благоприятный для C набор.

## Контроль сравнения

| Режим | Состав |
|---|---|
| A | Локальная LLM, подготовленные события, без RAG |
| B | Та же LLM и локальная выдача RAG |
| C | Фиксированные профили + RAG + шаблон; без семантической постпроверки D |
| D | **Тот же сохранённый черновик B**, программная проверка и адресные отказы |

Общие импорт, нормализация, допустимые поля, Case, схема и политика срочности.
Оценка приоритета измеряет общую политику, не эффект RAG/LLM.
A/B/C не получают скрытой семантической проверки. JSON-структура проверяется во всех режимах.

На каждый повтор B генерируется один раз. D читает его DraftBundle; `draft_id`
совпадает, `measurement.draft_reused=true`, origin_run_id указывает B.
Если выбран только D, внутренний B формирует черновик, но не добавляет строку B в метрики.
Если B не сформировал черновик, D получает `paired_draft_unavailable` без новой генерации.
Для генеративных вариантов требуется минимум три повтора. C выполняется один раз на случай.
Seed, модель, параметры и промпт общие; Llama.reset вызывается перед генерацией A/B.

`total` — измеренный проход конкретного вызова анализа, `verification` — отдельный
интервал работы verifier. В D replay `total` содержит повторную проверку без новой генерации.
`full_pass` у парного D — **составное** время: общая подготовка + интервалы priority,
retrieval и generation_or_rules исходного B + текущий проход D. Оно включает повторный
расчёт приоритета и накладные расходы D; это явно помеченная оценка полного прохода,
не независимый замер второй генерации. Исходные интервалы сохранены в measurement.
Для A/B/C full_pass — измеренный анализ плюс подготовка. Загрузка модели также записана
отдельно; generation_or_rules уже включает её, повторно прибавлять model_load нельзя.

## Независимая оценка

`evaluation.py` не импортирует verifier/profiles и проверяет значения по raw текущей
записи, а допустимые техники и приоритет — по отдельному gold. supported не является
эталоном истинности. Отклонённые техники не входят в положительные ответы;
analyst_required учитывается как предложенный кандидат. `confirmed_technique_share`
и число кандидатов показываются отдельно и не являются метрикой истинности.

Все отношения сохраняются в `summary[mode].metrics[name]` как
`{numerator, denominator, value, applicable}`. При denominator=0: value=null,
applicable=false. Старые плоские имена метрик оставлены для совместимости.

| Показатель | Числитель / знаменатель |
|---|---|
| precision | TP / (TP+FP) |
| recall | TP / (TP+FN) |
| f1 | 2TP / (2TP+FP+FN) |
| fact_reference_accuracy | Точные raw-ссылки фактов / заявленные факты |
| evidence_reference_accuracy | Точные raw-ссылки техник / все ссылки техник |
| evidence_completeness | Техники с полным набором процитированных обязательных полей одной записи / предложенные техники |
| unsupported_technique_claim_rate | Техники вне gold либо с недостаточными/неверными доказательствами / предложенные техники |
| unsupported_structured_claim_rate | Неверные факты + неподтверждённые техники / факты + предложенные техники |
| annotated_fact_coverage | Выданные как факты точные размеченные assertions / размеченные assertions |
| technique_opportunity_coverage | Выданные заключения среди размеченных возможностей / все возможности заключения либо отказа |
| priority_accuracy | Точное совпадение категории с gold / случаи-повторы |
| priority_coverage | Выдана определённая категория / случаи-повторы с возможностью определить категорию либо отказаться |
| coverage | Случаи без технического сбоя и с предложенной техникой / все случаи-повторы |
| partial_fact_coverage | Случаи без технического сбоя с фактами / все случаи-повторы |
| technical_error_rate | Технические ошибки / все случаи-повторы |

TP/FP/FN определяются по множеству уникальных ID на случай-повтор. Пропущенный
правильный ID даёт FN, даже если D обоснованно отклонил другой неверный ID черновика.
Поддельная ссылка может корректно отклоняться verifier и одновременно снижать полноту
итогового анализа достаточного случая: эти выводы различаются.
Общие свободные гипотезы и рекомендации не включаются в автоматическую долю
проверяемых структурированных утверждений; для них требуется аналитик.

Отказы измеряются на двух уровнях:

- Случай: отказ при отсутствии выданных техник, наличии refusal/abstained и отсутствии
  технической ошибки. TP_refusal/FP_refusal/FN_refusal сверяются с should_abstain.
- Возможность по технике: адресный отказ или явно названный ID в декларации; общий
  текстовый отказ не переносится автоматически на все отдельные техники.
  Сохраняются claim_outcomes, correct/excess/expected refusal и sufficient counters.

refusal_precision = обоснованные / все отказы; refusal_recall = обоснованные /
ожидаемые отказы; unjustified_refusal_rate = избыточные / достаточные случаи.
У claim_refusal_precision/recall/claim_excess_refusal_rate тот же принцип на уровне
размеченных возможностей. Технический сбой не считается обоснованным отказом.
Пустой ответ не получает идеальную precision: она null, полнота на положительном случае 0.

Счётчики приоритетов over/under/unknown_mismatch выводятся отдельно.
Для времён сохранены индивидуальные значения, сумма, число наблюдений, среднее;
для успешного анализа — также медиана и выборка. Смешивать replay latency с реальной
генерацией нельзя. Незаполненные ручные оценки остаются null.

## Штатные команды

Из папки `local-soc-assistant` после установки/prepare --index:

```powershell
$PythonExe = ".\.venv\Scripts\python.exe"
# Прежний корпус C; модель не требуется.
& $PythonExe -m soc_assistant.cli experiment --modes C --split all --out data\C-all
# Реальная модель: сначала настройка, затем фиксированная тестовая выборка.
& $PythonExe -m soc_assistant.cli experiment --modes A B C D --repeats 3 --split tune --out data\tune
& $PythonExe -m soc_assistant.cli experiment --modes A B C D --repeats 3 --split test --out data\test
# Контроль механики без LLM и сети: A/B читают явно обозначенные сохранённые Draft.
& $PythonExe -m soc_assistant.cli experiment --modes A B C D --repeats 3 --split all --gold evaluation\controls.json --replay-dir examples\drafts --out data\controls
# Самостоятельный verifier, без вызова LLM:
& $PythonExe -m soc_assistant.cli demo --mode C --out data\demo-C
& $PythonExe -m soc_assistant.cli verify --bundle data\demo-C\draft.bundle.json --out data\verified
```

`--replay-dir` — **контроль механики**, не реальная генерация. A и B в этих fixtures
намеренно одинаковы; эффект RAG по ним не измеряется. plan.experiment_kind и backend
указывают SAVED_DRAFT_TEST_FIXTURE, real_llm=false. Сравнение качества LLM требует
установленной локальной модели и запуска без --replay-dir.

Артефакты: plan.json (выборка, версии, хеш gold, параметры), drafts/ (Case+Draft+источники),
run-*.json (Report/checks/times), individual.json (независимая оценка), summary.json
(счётчики и знаменатели), analyst-review.csv (пустая независимая ручная разметка).
Отчёты указывают draft_id; raw хранится в общем bundle, не в каждом Report.
Сбой/отмена не удаляет ранее сохранённые результаты. Коды CLI: 0 завершено,
2 техническая ошибка/неготовность, 3 ошибки импорта, 4 занята задача.

Фактические результаты доработки находятся в validation/upgrade-20261122/;
описание границ измерений — VALIDATION.md. Старые validation/comparison и прочие
каталоги сохранены как история предыдущей версии и не подтверждают текущий код.
