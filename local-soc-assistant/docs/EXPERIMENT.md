# Методика сравнительной оценки

## Цель и ограничения

Сравнить влияние поиска и доказательной постпроверки на воспроизводимом инженерном корпусе.
Нулевая гипотеза о превосходстве D не подменяется ожиданием разработчика.
24 сценария / 12 семейств не достаточны для обобщений о реальном SOC.
Варианты семейства не являются независимыми наблюдениями; повторы LLM также не увеличивают
число независимых сценариев. Статистическая значимость и доверительные интервалы по этому набору не заявляются.

## Фиксация данных

`evaluation/gold.json` содержит ожидаемые наблюдаемые техники, очередь проверки, требование отказа
и обязательные поля доказательств. Синтетические сценарии злонамеренной и легитимной активности могут
иметь одинаковую технику: ATT&CK описывает поведение, не служит меткой злонамеренности.
`malicious_simulation` — известное автору намерение сценария, не факт, доступный анализатору.
Тестовые эталоны, метки и способы мутаций в `evaluation/adversarial.json` не индексируются.

Генератор и эталоны зафиксированы до запуска сравнения. Split осуществляется по семействам.
Настройка промпта должна выполняться на `--split tune`, итоговая оценка — `--split test`.
Разработчик знает устройство инженерного корпуса: это не слепое внешнее испытание.
Синтетические данные тесно согласованы с узкими правилами, что благоприятно для C;
идеальные показатели C на них не означают высокое качество на произвольной телеметрии.

## Контроль переменных

A/B/D: одинаковая модель, параметры, схема JSON и представление событий.
B/D: одна функция поиска, одинаковые top_k, снимок, индекс и формат фрагментов.
A: отсутствие RAG. C: фиксированные правила с обязательным наличием найденного определения.
Постпроверка D не выполняется для A/B. Их неверные значения сохраняются для оценки.
Детерминированная политика приоритета общая для всех четырёх режимов; измерение её качества
оценивает саму политику, а не эффект RAG/LLM. Это ограничение дизайна явно учитывается.

Генеративные режимы запускаются минимум три раза. Seed фиксирован при поддержке,
индивидуальные результаты сохраняются даже при одинаковом тексте. Время первой загрузки
не смешивается с временем тёплых запусков: отдельно записаны `model_load` и полное время.
Построение индекса выполняется до запуска и измеряется отдельной командой/протоколом подготовки.
Нельзя удалять ошибочные ответы или выбирать лучший повтор.

## Автоматические метрики

Единица сопоставления ATT&CK — уникальный ID на случай/повтор. Отклонённые D техники не считаются
итоговыми положительными ответами. `analyst_required` считается предложенной, но не подтверждённой техникой.
Дубликаты ID не увеличивают TP. Для микросредних суммируются TP/FP/FN по всем попыткам режима.

- `TP`: ID в результате и эталоне; `FP`: только в результате; `FN`: только в эталоне.
- Precision = TP / (TP + FP).
- Recall = TP / (TP + FN).
- F1 = 2TP / (2TP + FP + FN).
- Точность приоритета = точные совпадения / все попытки.
- Завышение/занижение: сравнение порядков low < medium < high.
  Несовпадения с unknown учитываются отдельно, а не как низкий уровень.
- Точность ссылок фактов = число точных event_id/field/value / число заявленных фактов.
- Полнота доказательств = число предложенных техник с полным набором корректно процитированных
  обязательных полей хотя бы одного события / число предложенных техник.
- Доля неподтверждённых технических утверждений = число предложенных техник вне эталона,
  с неполными обязательными доказательствами или неверными ссылками / число предложенных техник.
  Это **ограниченная автоматическая** оценка, не оценка всех свободных гипотез и рекомендаций.
- Покрытие = попытки без технического сбоя и хотя бы с одной предложенной техникой / все попытки.
- Покрытие частичными фактами = попытки без сбоя и с фактами / все попытки.
- Доля технических ошибок = технические ошибки / все попытки.

Для оценки отказов на уровне случая:

- Ожидаемый отказ: у сценария нет достаточных оснований для поддерживаемого вывода.
- Фактический отказ: нет предложенных техник, нет технической ошибки, есть отказ либо статус abstained.
- TP_refusal: обоснованный отказ; FP_refusal: отказ на достаточных данных;
  FN_refusal: отсутствие требуемого отказа, включая технический сбой.
- Precision_refusal = TP_refusal / (TP_refusal + FP_refusal).
- Recall_refusal = TP_refusal / (TP_refusal + FN_refusal).
- Необоснованные отказы = FP_refusal / число попыток на достаточных данных.

Частичные отказы по отдельным гипотезам сохраняются, но основная агрегированная метрика отказов
является метрикой случая. Для полноценного анализа частичных отказов требуется отдельная разметка утверждений.

Нулевой знаменатель → JSON null («не определено»), не 0 и не 1.
Пустой ответ на положительный сценарий даёт FN и нулевое покрытие. При отсутствии утверждений
доля неподтверждённых утверждений равна null и не трактуется как идеальное качество.
Отдельно выводится число пустых ответов. Техническая ошибка не считается корректным отказом.
Среднее и медиана времени содержательных/нетехнических завершений выводятся вместе с числом ошибок;
время каждой ошибочной попытки остаётся в индивидуальном результате.

## Проверка аналитиком

Автоматический оценщик не проверяет истинность произвольных русских объяснений,
разумность свободных рекомендаций A/B или наличие скрытых предположений в гипотезах.
`analyst-review.csv` содержит пустые поля оценки и замечания; неподготовленные значения остаются null.
Аналитику нужно проверить утверждения по событиям и источникам, отдельно отметить:
смысловую корректность rationale, необоснованные интерпретации и применимость рекомендаций.
Нельзя заменять эту разметку оценкой LLM или придуманными баллами.

## Запуск

```powershell
$PythonExe = ".\.venv\Scripts\python.exe"
& $PythonExe -m soc_assistant.cli experiment --modes C --split all --out data\C-all
& $PythonExe -m soc_assistant.cli experiment --modes A B C D --repeats 3 --split tune --out data\tuning
& $PythonExe -m soc_assistant.cli experiment --modes A B C D --repeats 3 --split test --out data\test
```

`plan.json` фиксирует выборку, режимы, число повторов, хеш эталонов и конфигурации.
`individual.json` — строки оценки всех запусков; `run-*.json` — исходные и итоговые отчёты;
`summary.json` — агрегаты; `analyst-review.csv` — ручная разметка.

Дополнительно выводится `unsupported_structured_claim_rate`:
(неверные факты + неподтверждённые техники) / (все факты + предложенные техники).
Свободные гипотезы и обоснования в этот автоматический знаменатель не включены и требуют разметки.
Коды завершения CLI: 0 — завершено, 2 — техническая ошибка/неготовность,
3 — ошибки импорта, 4 — уже выполняется другой анализ.

В итоговом рантайме перед каждой генерацией вызывается `Llama.reset()`: веса остаются в RAM,
но не используется совпавший префикс предыдущего запроса. Это относится и к форматному исправлению.
Поле runtime.prompt_state_reset_per_generation фиксирует эту политику.
Ранний инженерный прогон, где это поле отсутствует, нельзя использовать для сравнительных
выводов о времени A/B/D: там рантайм мог повторно использовать префикс предыдущего запроса.
